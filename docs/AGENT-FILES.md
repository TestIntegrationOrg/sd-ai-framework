# Agent Files and Skills

SD-AI v0.5 separates **semantic agent roles** from **execution provider profiles**.

A semantic agent answers: *who is responsible for this lifecycle job and what rules/skills apply?*

A provider profile answers: *which executable/model adapter runs that job?*

This separation lets the same `architect` role run through Claude, Codex, Copilot, Gemini, or a custom provider without duplicating architecture instructions.

## Source of truth

```text
.sdai/
├── agents/
│   ├── requirements-analyst.agent.md
│   ├── architect.agent.md
│   ├── planner.agent.md
│   ├── developer.agent.md
│   ├── code-reviewer.agent.md
│   ├── tester.agent.md
│   ├── security-reviewer.agent.md
│   └── documentation-writer.agent.md
└── agent-routing.yaml

.agents/
└── skills/
    ├── requirements-analysis/
    │   ├── SKILL.md
    │   └── sdai.yaml
    ├── architecture-design/
    ├── architecture-review/
    ├── implementation-planning/
    ├── spec-traceability/
    ├── secure-coding/
    ├── test-design/
    └── documentation-quality/
```

Edit these canonical files. Provider-native agent files generated by SD-AI are derived artifacts.

## Canonical `.agent.md` format

```markdown
---
name: architect
description: Generate architecture options and ADR proposals.
capabilities: [architecture, review]
skills: [architecture-design, architecture-review, spec-traceability]
profile: claude
execution_mode: advisory
providers:
  codex: {}
  copilot: {}
  claude: {}
  gemini: {}
---
# Architect

Derive architecture drivers from approved requirements and NFRs.
Generate viable alternatives, compare trade-offs, and propose ADRs.
```

Required metadata:

- `name`: lowercase kebab-case and equal to the file name before `.agent.md`.
- `description`: concise purpose used for discovery/export.
- `capabilities`: one or more SD-AI lifecycle capabilities.

Optional metadata:

- `skills`: canonical shared skills attached to this semantic role.
- `profile`: default provider profile if the caller does not override one.
- `execution_mode`: used by provider-native export; SD-AI runtime still requires workflow/CLI write permission explicitly.
- `providers`: non-secret provider-native metadata overrides.

Credential-like provider keys such as tokens, passwords, secrets, API keys, credentials, and private-key fields are rejected. Keep authentication in provider-native credential stores or environment/configuration mechanisms outside agent files.

## Agent routing

`.sdai/agent-routing.yaml` maps lifecycle capability to default semantic role:

```yaml
version: 1
routes:
  requirements: requirements-analyst
  architecture: architect
  planning: planner
  coding: developer
  review: code-reviewer
  testing: tester
  security: security-reviewer
  documentation: documentation-writer
```

Provider routing remains separate in `.sdai/routing.yaml` and provider details remain in `.sdai/agents.yaml`.

Resolution order for a runtime invocation is:

```text
explicit --agent
        ↓
agent-routing.yaml
        ↓
semantic agent definition
        ↓
default semantic profile (unless --profile overrides it)
        ↓
provider profile
```

If a project has no v0.5 semantic agent files, the v0.4 provider/capability routing path remains valid.

## Shared `SKILL.md` format

Canonical skills use a portable `SKILL.md` with minimal frontmatter:

```markdown
---
name: architecture-design
description: Design architecture from explicit drivers and trade-offs.
---
# Architecture Design

- Derive architecture drivers before selecting technology.
- Generate multiple viable options for material decisions.
- Record material choices as ADR proposals.
```

SD-AI-specific capability metadata lives next to it in `sdai.yaml` rather than polluting portable skill frontmatter:

```yaml
version: 1
capabilities: [architecture]
```

If both `.agents/skills/<name>` and legacy `.sdai/skills/<name>` exist, the canonical `.agents/skills` version wins. Legacy skill projects continue to work.

## Provider-native synchronization

Generate native agent files from the canonical SD-AI definitions:

```bash
sdai agents sync --provider all
```

Or one provider:

```bash
sdai agents sync --provider codex
sdai agents sync --provider copilot
sdai agents sync --provider claude
sdai agents sync --provider gemini
```

Generated locations:

```text
Codex       .codex/agents/<name>.toml
Copilot     .github/agents/<name>.agent.md
Claude      .claude/agents/<name>.md
Gemini      .gemini/agents/<name>.md
```

The shared `.agents/skills` directory is kept as the canonical skill source. SD-AI mirrors canonical skills into `.claude/skills` when synchronizing Claude because Claude uses its project-native skill directory. Other supported providers can consume the shared skill source directly.

Generated agent files contain an SD-AI marker. A later sync can update those files. SD-AI refuses to overwrite an unmarked, hand-authored provider-native agent unless `--force` is explicit:

```bash
sdai agents sync --provider copilot --force
```

Use `--force` only when you intentionally want the canonical SD-AI definition to replace a native customization.

## Inspect semantic agents

```bash
sdai agents definitions
sdai agents show architect
```

Provider profiles are still shown separately:

```bash
sdai agents list
sdai agents doctor
```

## Run a semantic agent

Use the default semantic role and provider routing:

```bash
sdai agents run architecture FEATURE-123 --dry-run
```

Select a role explicitly:

```bash
sdai agents run architecture FEATURE-123 \
  --agent architect \
  --dry-run
```

Override only the provider profile:

```bash
sdai agents run architecture FEATURE-123 \
  --agent architect \
  --profile codex \
  --dry-run
```

The semantic `architect` instructions and skills remain the same; only the provider changes.

## Workflow integration

Agent steps can now name both semantic agent and capability:

```yaml
- id: architecture-review
  type: agent
  agent: architect
  capability: architecture
  mode: advisory
```

A workflow may still pin a provider profile if required:

```yaml
- id: architecture-review
  type: agent
  agent: architect
  capability: architecture
  profile: codex
  mode: advisory
```

For provider-independent workflows, omit `profile` and let the semantic-agent/provider routing layers resolve it.

Manual execution keeps both overrides independent:

```bash
sdai step run FEATURE-123 architecture-review \
  --workflow enterprise \
  --agent architect \
  --profile codex \
  --dry-run
```

## Security rules

- Agent and skill files are version-controlled executable guidance; review changes like code.
- Never store API keys, tokens, passwords, private keys, or provider credentials in `.agent.md`, `SKILL.md`, or `sdai.yaml`.
- External issue text, source text, logs, scanner output, and generated artifacts remain untrusted data and cannot override system/governance instructions.
- Provider-native write permissions remain constrained by the selected execution mode and provider adapter.
- Generated native files are derived artifacts; canonical SD-AI definitions remain the source of truth.
