# Typed Trace Evidence Contract

SDAI 0.10 defines a provider-neutral evidence record for facts that can become canonical proof in the traceability graph.

## API version

Every serialized record uses:

```text
sdai.trace-evidence/v1
```

Unknown fields, unknown enum values, malformed hashes, unsafe paths, non-finite JSON, and unbound records fail closed.

## Evidence kinds

The v1 finite evidence kinds are:

- `execution`
- `test`
- `quality`
- `security`
- `approval`
- `review`
- `operational`

Statuses are finite as well: `passed`, `failed`, `blocked`, or `recorded`. Kind-specific decision details such as an approval decision or scanner result belong in the typed JSON `result` payload rather than changing the global status vocabulary.

## Canonical record

A record contains:

- `evidence_id`: portable stable evidence identifier.
- `kind` and `status`: finite enums.
- `subject`: the semantic entity the evidence claims to support. Trace-node resolution is performed by later trace integration.
- `git_commit`: a normalized 40- or 64-hex Git commit identity.
- `bindings`: one or more SHA-256 content bindings. A record without a content binding cannot become canonical evidence.
- `command`: executable/argv array. Shell command strings are rejected to avoid ambiguous command interpretation.
- `tool`: optional tool identity.
- `result`: bounded finite JSON only; NaN, infinity, arbitrary Python objects, excessive nesting, and excessive item counts are rejected.
- `provenance`: one or more repository-relative source/line declarations using the same `TraceProvenance` contract as the canonical trace graph.
- `producer`: semantic role plus optional provider/model metadata.
- `truth_sha256`: SHA-256 of the provider-independent evidence claim.
- `sha256`: SHA-256 of the complete canonical record, including producer metadata and `truth_sha256`.

## Provider-independent truth

`producer.semantic_role`, `producer.provider`, and `producer.model` identify how a record was produced, but provider/model selection is not evidence truth.

The `truth_sha256` excludes the producer object. Therefore the same evidence claim generated by different model providers has the same truth identity. The complete `sha256` still changes when producer metadata changes, preserving auditability without coupling trace coverage to a vendor or model.

This separation is required for deterministic provider-neutral linking and later freshness/revalidation rules.

## Content bindings

Bindings use exactly:

```json
{
  "kind": "source",
  "source": "src/signing/service.py",
  "sha256": "sha256:<64 lowercase hex characters>"
}
```

Supported binding kinds are `artifact`, `source`, `test`, and `evidence`.

Binding paths must be repository-relative POSIX paths. Absolute paths, Windows drive paths, backslashes, `.` segments, and `..` traversal are rejected. Duplicate identical bindings collapse deterministically; conflicting hashes for the same kind/path fail closed.

The Git commit is kept as an explicit top-level binding because repositories may use SHA-1 or SHA-256 object formats, while all content identities in the evidence model are SHA-256.

## Determinism

Canonical JSON is UTF-8, key-sorted, compact JSON with non-ASCII text preserved. Binding and provenance order are canonicalized before hashing. Input ordering therefore cannot change the evidence identity.

Two identities are exposed:

- `truth_sha256`: canonical evidence truth, independent of provider/model metadata.
- `sha256`: complete record identity for durable storage and tamper detection.

Serialized records carry both values. Loading recomputes both and rejects mismatches.

## Durable loading and path safety

`load_trace_evidence(project_root, path)` only reads regular non-symlink files contained by the repository root. Symlink components, traversal outside the project, invalid UTF-8, malformed JSON, and hash tampering are rejected.

Evidence files are expected to live under repository-owned durable locations such as execution/task evidence directories. Consumers should store the evidence file itself and bind referenced sources/artifacts by SHA-256 rather than relying on transient provider output.

## Generic validation API

```python
from sdai.trace_evidence import validate_trace_evidence

record = validate_trace_evidence(raw_json_or_mapping)
```

The validator is intentionally independent of the execution ledger, quality gates, and integrations. Those systems can adopt the contract without becoming the source of truth for evidence semantics.

## Error families

- `SDAI-EVIDENCE-001`: schema, enum, text, or finite-JSON violations.
- `SDAI-EVIDENCE-002`: commit/content binding violations.
- `SDAI-EVIDENCE-003`: command representation violations.
- `SDAI-EVIDENCE-004`: provenance violations.
- `SDAI-EVIDENCE-005`: producer metadata violations.
- `SDAI-EVIDENCE-006`: serialization, version, and integrity violations.
- `SDAI-EVIDENCE-007`: durable path/loading violations.

## Relationship to the trace graph

`sdai.trace-evidence/v1` is the evidence payload contract. `sdai.trace-graph/v1` is the canonical relationship graph. This slice intentionally does not infer coverage or mutate graph edges. The next SDAI 0.10 integration slices consume validated evidence and link it to trace nodes under explicit deterministic rules.
