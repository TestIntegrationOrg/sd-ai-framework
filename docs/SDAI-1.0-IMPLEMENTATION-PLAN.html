SDAI 1.0 — Complete Implementation Plan

A complete implementation program to evolve SDAI into a governed AI Software Development Lifecycle platform. It incorporates the strongest concepts identified from GitHub Spec Kit, Fission-AI OpenSpec, and obra/superpowers while preserving SDAI's enterprise policy, semantic agents, architecture, security, provider routing, approvals, quality gates, and deterministic source-of-truth model.

Updated: 2026-08-11Target: SDAI 1.0Engineer + EnterpriseExtension-firstEvidence-driven

1. Executive Summary

SDAI should not win by accumulating prompts or commands. It should become the engineering control plane that can prove how software moves from intent to specification, architecture, implementation, verification, approval, and delivery across AI providers, languages, teams, and repositories.

Target positioning: Spec Kit contributes rigorous SDD quality; OpenSpec contributes fluid brownfield change management; Superpowers contributes disciplined agentic execution; SDAI should govern all three under one enterprise-ready architecture.

Non-negotiable outcomes

  • New skills, language/framework skills, semantic agents, workflow components, workflows, schemas, validators, gates, integrations, and packs normally require no SDAI core Python changes.
  • The deterministic SDAI engine owns canonical state, policy enforcement, source-of-truth promotion, evidence, staleness, approvals, and traceability.
  • AI agents propose, analyze, implement, debug, and review but do not self-approve policy, requirements, architecture, or delivery evidence.
  • Fluid iteration is allowed, but every downstream artifact and approval affected by a change becomes explicitly stale.
  • Language/framework/platform/library expertise is dynamically selected based on role, task, affected files, repository technology, risk, and policy.
  • Skills and agents are measurable through evaluation scenarios; they are not trusted merely because their prompt looks good.
  • No completion claim is accepted without fresh machine evidence appropriate to the claim.
  • Long-running execution survives context loss through a durable execution ledger.
  • All major read/analysis/status operations expose versioned JSON contracts.

3. Product Goal

SDAI is a governed engineering lifecycle for humans and AI—from intent and requirements through architecture, implementation, verification, and delivery—across providers, languages, repositories, and enterprise boundaries.

SDAI 1.0 must answer: what requirement drove a change; which architecture decision authorized it; which semantic agent/provider/model/skills performed AI work; what code and tests implement it; which security/quality checks passed; who approved it; what current specification is true; and whether code still conforms to approved architecture/contracts.

4. Architecture Principles

Extension-first

At least 90% of company-specific behavior should be achievable with Markdown, YAML/manifests, schemas, packs, and reusable components.

Deterministic engine owns truth

Canonical state, promotion, policy, staleness, approvals, evidence, and traceability are framework-owned.

Semantic role != provider

Architect/developer/debugger/reviewer are roles; Claude/Codex/Copilot/Gemini/Cursor/etc. are execution choices.

Fluid but governed

Iteration is permitted; dependent artifacts and approvals become stale automatically.

Evidence over claims

Success status comes from current evidence, not agent confidence or stale previous runs.

Context isolation

Fresh task workers get minimal relevant context and explicit task contracts instead of inherited conversational history.

Least privilege

Advisory default, explicit workspace writes, protected paths, minimal env, plugin permissions, and optional workspace isolation.

Stable machine contracts

Versioned JSON is the automation API; human-readable text is presentation.

12. Artifact Dependency Graph and Staleness

requirements
   ├── architecture → ADR / contracts / threat-model
   ├── tests
   └── plan → tasks → implementation evidence

When requirements or architecture changes, hashes drive deterministic staleness. Architecture review, plans, tasks, implementation validation, tests, and approvals are invalidated according to dependency rules and policy.

Artifact schema

apiVersion: sdai/v1
kind: ArtifactSchema
metadata: { id: enterprise-feature }
spec:
  artifacts:
    requirements: { required: true }
    architecture: { requires: [requirements] }
    threat-model:
      requires: [architecture]
      required_when: { risk: [critical, regulated] }
    contracts: { requires: [architecture] }
    plan: { requires: [architecture, contracts] }

13. SDD Quality Loop

Engineering constitution

.sdai/constitution.md defines engineering principles distinct from execution policy. Constitution hash is included in relevant run/approval evidence.

sdai constitution init
sdai constitution validate
sdai constitution check FEATURE-123

Clarification

sdai clarify addresses functional behavior, actors/permissions, inputs/outputs, failures, edge cases, state transitions, security, performance, compatibility, observability, deployment, rollback, retention, and compliance.

Requirements checklist

Structured RQ findings cover completeness, ambiguity, testability, conflict, boundaries, observability, traceability, failure awareness, security, compatibility, and measurable NFRs. Reviewer-owned checks cannot be self-approved by implementation agents.

Analyze

Read-only cross-artifact analysis detects ORPHAN_REQUIREMENT, ORPHAN_TASK, MISSING_NFR, ARCHITECTURE_CONFLICT, CONTRACT_CONFLICT, UNRESOLVED_ADR, UNTESTED_SCENARIO, UNAPPROVED_BREAKING_CHANGE, UNMITIGATED_THREAT, and STALE_ARTIFACT.

Verify + converge

Deterministic evidence checks task state, artifacts, trace links, tests, quality gates, contracts, approvals, hashes, and staleness. Semantic review checks actual requirement satisfaction, architecture intent, failure behavior, and undocumented behavior. Bounded convergence converts approved gaps into remediation tasks and repeats.

Trust boundary: implementation agents may never rewrite requirements merely to make verification agree with their own code.

17. Evidence-Before-Completion Engine

“Agent said success” is not evidence. Completion claims must be backed by current machine-verifiable evidence.

Agent: "Tests pass"
SDAI: locate TEST_EXECUTION evidence for current commit/artifact hash
none → CLAIM_UNVERIFIED → task cannot transition to verified

Evidence binding

completion:
  require_fresh_evidence: true
  require_current_commit: true
  evidence: [tests, build]

Critical policy can additionally require security scan, contract validation, traceability threshold, and review evidence.

Freshness

Changing relevant code invalidates prior test/build evidence. Changing requirements/architecture can also invalidate semantic verification and approvals.

Structured evidence types

TEST_EXECUTION, BUILD, LINT, SAST, SCA, TRIVY, SONAR, CONTRACT_VALIDATION, TRACEABILITY, REVIEW, APPROVAL, DEPLOYMENT_DRY_RUN.

18. Isolated Task-Agent Execution and Independent Review

Support a coordinator strategy that dispatches a fresh worker per task with minimal task context and explicit interfaces, then requires independent gates.

Coordinator
  ├── TASK-1 → fresh developer → spec review → code-quality review
  ├── TASK-2 → fresh developer → spec review → code-quality review
  └── final whole-change reviewer

implementation:
  strategy: isolated-task-agents
  implementer:
    agent: developer
  review:
    - type: spec-compliance
      agent: requirements-analyst
    - type: code-quality
      agent: code-reviewer
  final_review:
    agent: code-reviewer

Task contract

Each task contains exact affected paths, requirement IDs, interfaces consumed/produced, constraints, expected tests, verification commands, and completion evidence. Task size is based on independent understandability/testability/reviewability—not an arbitrary clock duration.

Fix-loop behavior

Bounded review/fix rounds, escalation to more capable model or human when repeated failures indicate ambiguity or architectural problems, and no infinite agent retry loop.

  • Run dependency/bootstrap setup.

31. Acceptance Criteria

Extension journeys

  • Skill: create → validate → eval → attach → execute with no core code changes.
  • Agent: create/inherit → validate → eval → execute on any allowed provider with no hard-coded registry change.
  • Workflow: create/extend/overlay → validate → resolve → run with no orchestrator changes.
  • Language expertise: existing developer dynamically receives Java/Spring/Jsign skills for Java task and PowerShell/AuthentiCode skills for PS task; agent identity remains unchanged.

Execution excellence journeys

  • A skill eval demonstrates measurable improvement over baseline and records provider/model variance.
  • A long run can be interrupted and resumed without redispatching completed tasks.
  • An agent cannot mark tests/build/verification complete without current evidence.
  • A critical task is executed by a fresh worker, independently reviewed for spec compliance and code quality, and final-review evidence is persisted.
  • Systematic debugging records reproduction, hypothesis, experiment, root cause, regression evidence.
  • Worktree mode records clean baseline test evidence before implementation.

36. Definition of “Better Than Spec Kit, OpenSpec, and Superpowers”

Success is not stars, number of prompts, or number of commands. SDAI is better when the integrated engineering guarantee is stronger.

North star: SDAI can prove why software was built, which requirement drove it, which architecture decision authorized it, which AI/human changed it, which provider/model/skills were used, whether those skills are evaluated, which tests/security/quality checks passed with fresh evidence, what current specification is true, and whether implementation still conforms to approved architecture and contracts.
Spec Kit strength:      SDD quality
OpenSpec strength:      fluid change/spec lifecycle
Superpowers strength:   disciplined agentic implementation
SDAI unique layer:      enterprise governance + architecture + security + traceability + provenance

SDAI 1.0 = all four concerns integrated under one deterministic policy model
