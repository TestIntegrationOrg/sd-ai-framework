SDAI 1.0 — Complete Implementation Plan

A roadmap to evolve SDAI into a governed AI Software Development Lifecycle platform that combines the strongest ideas from GitHub Spec Kit and OpenSpec while preserving and extending SDAI's enterprise policy, semantic-agent, architecture, security, approval, quality-gate, and provider-routing model.

Plan date: 2026-08-11 Target: SDAI 1.0 Primary users: engineers, architects, enterprise platform teams Design rule: extension-first

1. Executive Summary

SDAI should not compete by having more prompts or more commands. It should become the engineering control plane that can explain and prove how software moves from intent to specification, architecture, implementation, verification, approval, and delivery across multiple AI providers and repositories.

Target positioning: GitHub Spec Kit is an excellent rigorous SDD toolkit. OpenSpec is an excellent lightweight and fluid change-specification system. SDAI should become the governed AI engineering lifecycle that includes rigorous SDD, fluid brownfield changes, deep architecture engineering, enterprise security, traceability, multi-agent execution, and multi-repository coordination under one policy model.

Non-negotiable design outcomes

  • New skills, language/framework skills, semantic agents, workflow components, workflows, validators, quality gates, integrations, and packs should normally be added without modifying SDAI core Python.
  • The deterministic SDAI engine owns canonical truth; AI agents propose, reason, implement, and review but do not self-approve policy or source-of-truth transitions.
  • Fluid iteration must be allowed, but artifact staleness and invalidated approvals must be explicit and enforceable.
  • Language/framework expertise must be dynamically resolved based on repository technology, task scope, role, feature risk, and enterprise policy.
  • Every important lifecycle state must have a stable machine-readable JSON representation suitable for CI and future web tooling.

3. Product Goal

SDAI is a governed engineering lifecycle for humans and AI—from intent and requirements through architecture, implementation, verification, and delivery—across providers, repositories, and enterprise boundaries.

SDAI 1.0 should be able to answer, for any delivered change:

  • Which requirement caused this code to exist?
  • Which architecture decision authorized the implementation approach?
  • Which provider/model/semantic agent performed each AI-assisted step?
  • Which skills and enterprise standards were applied?
  • Who approved the requirements/architecture/release state?
  • Which tests and quality/security gates prove the behavior?
  • Which specification version represents current truth after delivery?
  • Whether current code has drifted from approved architecture or contracts.

4. Architecture Principles

Extension-first

90% of organization-specific behavior should be achievable with Markdown, YAML/manifests, schemas, and reusable components. Core code changes are reserved for genuinely new runtime capabilities.

Deterministic engine owns truth

AI proposes and reasons. SDAI validates, persists canonical state, applies deltas, invalidates stale artifacts, enforces policy, records evidence, and promotes source-of-truth changes.

Semantic role != provider

architect, developer, and security-reviewer remain semantic roles. Codex, Claude, Copilot, Gemini, Cursor, and others are execution choices.

Fluid but governed

Engineers may revise requirements/design/tasks during implementation, but affected artifacts, approvals, and validation evidence automatically become stale when their inputs change.

Least privilege

Advisory remains default. Workspace-write is explicit. Protected paths, minimal provider environments, permission manifests, and enterprise policy remain foundational.

Stable machine contracts

Human-friendly CLI output is never the automation contract. Major read/analysis operations expose versioned JSON schemas.

24. Testing Strategy

Required test categories

  • Unit tests.
  • Integration tests.
  • CLI contract tests including JSON schemas.
  • Windows, Linux, and macOS behavior.
  • UTF-8 and subprocess boundary tests.
  • Upgrade/backward-compatibility tests.
  • Policy negative tests proving lower layers cannot weaken organization controls.
  • Path traversal, symlink, protected-path, secret/environment-isolation security tests.
  • Provider/integration manifest tests.
  • Golden/snapshot tests for artifact parsers and generators.
  • Mock-provider extension tests to avoid paid model dependency.
  • End-to-end lifecycle tests.

Mandatory reference journeys

Scenario A — Small Feature

Single repo, simple API change, lightweight risk profile, implementation + tests.

Scenario B — Critical Enterprise Feature

Requirements, clarification, RFC, ADR, OpenAPI, threat model, dual approval, implementation, security/quality gates, traceability, convergence, PR.

Scenario C — Multi-Repo Feature

Central spec store, API repo, UI repo, shared library, single requirement graph, per-repo tasks/PRs, cross-repo verification.

A release should not ship if these journeys fail.

25. Reliability, Provider Execution, and Performance

The framework must treat operational behavior as a product capability, especially after observed nested-provider timeout/no-output behavior.

Execution diagnostics

  • Prompt construction time.
  • Provider startup time.
  • Provider execution time.
  • First-output/heartbeat time.
  • Artifact parse/validation time.
  • Retry count and retry classification.
  • Context size/token metrics when exposed by provider.
sdai diagnostics FEATURE-123

Provider runtime requirements

Configurable timeout, streamed output where supported, progress/heartbeat reporting, cancellation, error classification, safe retries, actionable diagnostics, explicit UTF-8 boundaries, and predictable Windows/Linux subprocess handling.

UX rule: A long-running agent must not look frozen. Even when a provider cannot stream semantic output, SDAI should expose elapsed execution state and diagnostic context without leaking secrets.

27. Definition of “Better Than Spec Kit and OpenSpec”

Success is not measured by stars, number of commands, or copying features. SDAI is better when it provides a stronger integrated engineering guarantee.

North-star capability: SDAI can prove why software was built, what requirement drove it, which architectural decision authorized it, which AI/human changed it, which model/provider/skills were involved, which tests prove it, which security/quality controls passed, what current specification is true, and whether implementation still conforms to approved architecture and contracts.
