# SDAI 0.13 Release Evidence — Integration SDK + Ecosystem Expansion

This document is the release-evidence contract for milestone **0.13** / parent issue **#20**. The final gate is issue **#155** and must merge only after the exact candidate head passes the complete repository CI matrix on Ubuntu and Windows with Python 3.11 and 3.12.

## Release objective

0.13 turns external agent/IDE support into a versioned, declarative Integration SDK instead of a growing collection of hard-coded provider branches. A normal new Integration must be expressible through manifest/catalog/project data and must inherit SDAI's deterministic provenance, policy, path, execution, managed-file, repair, and automation contracts.

## Integrated reference journey

`tests/test_integration_sdk_release_gate_v013.py` creates a brand-new `release-gate-agent` at test runtime. That Integration does not exist in the packaged builtin catalog and requires no new provider/core Python branch. The positive journey proves, in order:

1. A repository manifest is discovered beside packaged builtins and resolves with exact repository provenance and manifest hash.
2. Exact and latest SemVer resolution are deterministic.
3. A runtime request binds raw Unicode/metacharacter input by hash without serializing the private input into request/plan JSON.
4. The execution plan uses one executable plus argv and passes dynamic input as one argument token; no shell is involved.
5. The portable test CLI executes successfully and returns normalized JSON while shell metacharacters remain literal data.
6. Native skill projection materializes exact source bytes with managed provenance and reaches `exact` status.
7. `sdai integration status --json` exposes the same exact manifest/status facts through the automation surface.
8. Deleting a managed native file produces repairable state; `repair_integration` restores the installed exact version.
9. Resolving a newer manifest produces deterministic `stale` status before upgrade.
10. Materializing the new version upgrades native bytes and install-state provenance; repeating the exact upgrade is byte/state idempotent.
11. Clean removal removes only owned managed bytes and leaves the install state empty.
12. The packaged `codex` and `generic-agents` Integrations and the custom CLI example remain discoverable alongside the runtime-added Integration.

That journey is the executable extension-first proof: an unknown harness is handled by generic SDK contracts rather than a new `if tool == ...` implementation.

## Fail-closed reference journey

The same release gate deliberately verifies the high-risk negative contracts required by #20/#155:

- a shell command string in `execution.executable` is rejected;
- traversal in a projection path is rejected;
- equal-precedence SemVer build variants make unqualified latest resolution ambiguous rather than arbitrary;
- a manifest cannot grant itself workspace-write when effective SDAI policy denies it;
- malformed JSON output becomes a stable `malformed-output` result;
- an unmanaged destination is never silently adopted, even when a materialization is requested;
- a user-modified managed file is preserved during removal instead of being deleted;
- symlink ancestry is classified as broken and cannot redirect managed writes outside the project (on platforms where symlink creation is available).

Additional focused 0.13 suites cover conflicting exact hashes, organization locks, environment filtering, invalid UTF-8, file-I/O ownership, timeout/cancellation, crash recovery, operation-journal tampering, path portability, selection-state hardening, lifecycle CLI errors, and all shipped ecosystem manifests.

## Architecture invariants retained

0.13 does not transfer canonical authority to external tools. SDAI still owns policy decisions, protected paths, managed-file ownership, provenance, and deterministic lifecycle state. Integrations may declare network/workspace/environment requirements, but effective SDAI policy is rechecked at plan/execution time and cannot be widened by a manifest.

The SDK remains project-native and shell-free. It does not silently manage user-home credentials/settings, interpolate runtime prompts into shell strings, overwrite unmanaged native files, transform incompatible provider-specific schemas by guesswork, or treat provider output as canonical truth.
