## Exact signed-Pack lifecycle evidence

`tests/test_pack_signed_lifecycle_gate_v012.py` composes the independent 0.12 contracts into one latest-head journey using Unicode paths/content so the same behavior is exercised on Windows and Linux:

1. **Manifest and resolution truth** — a canonical `publisher/id@version` Pack is resolved into an exact lock before materialization.
2. **Integrity and publisher authenticity** — signature verification binds the canonical manifest and Pack content hashes; post-signing content mutation invalidates the signature.
3. **Catalog and enterprise trust** — the exact artifact is selected from a trusted organization catalog and must satisfy the resolved non-weakening trust policy. Lower-level policy cannot disable required signatures or broaden organization publisher trust.
4. **Eval and certification freshness** — certification evidence is bound to exact Pack identity, manifest/content hashes, effective policy hash, current eval-suite hash, and exact case-input hashes. Changing the suite invalidates old evidence.
5. **Exact lifecycle materialization** — install consumes the exact lock and exact local artifact hashes, writes only under the framework-managed namespace, and is idempotent for the same state.
6. **Safe removal** — Pack-managed bytes that users modify are preserved rather than silently deleted.
7. **Resolver failure semantics remain deterministic** — missing dependencies and dependency cycles fail through the existing typed Pack-lock errors.

## Negative and fail-closed evidence

The 0.12 suite explicitly rejects or blocks:

- malformed/noncanonical manifest and lock input,
- ambiguous exact candidates, missing dependencies, incompatible constraints, and dependency cycles,
- Pack content changed after signing,
- signature evidence that no longer binds current content,
- catalog/publisher policy violations,
- attempts by repository/user policy to weaken organization requirements,
- install bytes that do not match the exact lock manifest/content hashes,
- unmanaged destination overwrite,
- modified managed-file overwrite or deletion,
- symlink/path traversal through managed destinations,
- interrupted lifecycle output whose bytes no longer match the operation journal,
- stale Pack/content/policy/eval-suite certification evidence,
- missing/failed required eval cases and dimensions, and
- producer/provider/model metadata attempting to influence provider-independent certification truth.

## Crash, retry, and idempotency evidence

The Pack lifecycle records an exact operation journal before managed mutation and commits canonical install state atomically. Tests prove:

- byte-identical interrupted output may be recovered only when a matching pre-existing journal proves ownership,
- an originally unmanaged destination never becomes managed merely by retrying,
- repeated exact installs converge on identical state,
- remove is idempotent for absent clean state, and
- user-modified Pack-managed bytes are preserved.

This extends rather than replaces the durable crash/resume and completion evidence already retained by the 0.9–0.11 full-suite gates.

## Cross-platform UTF-8 and path gate

0.12 tests intentionally include paths and content such as `café`, `éditeur`, and `Δ`, and the repository CI executes the complete suite under:

- Ubuntu / Python 3.11
- Ubuntu / Python 3.12
- Windows / Python 3.11
- Windows / Python 3.12

This matrix is the compatibility acceptance gate for path separators, UTF-8 I/O, canonical hashing, atomic state behavior, and Pack lifecycle semantics.

## Release gate

SDAI 0.12 is releasable only when all of the following are true on the **same exact candidate head**:

1. the complete CI matrix above succeeds;
2. the signed-Pack integration gate succeeds on all four matrix entries;
3. all 0.6–0.11 regression tests remain green in that same complete suite;
4. no Pack-specific negative test is skipped to obtain a green candidate; and
5. any integration defect discovered by #140 is fixed and revalidated at a new exact head before merge.

The final merged commit/PR and its GitHub Actions run provide the immutable candidate-head evidence; this document describes what that run must prove.
