# SDAI 1.0 Install, Upgrade, and Rollback Release Gate

Issue: #286

This document defines the release-blocking installation and migration safety evidence for SDAI 1.0. It complements the lifecycle reference journeys in `docs/releases/1.0-reference-journeys.md`.

## Clean package installation

Every supported CI leg runs `tests/package_install_smoke.py` after the complete unfiltered `pytest -q` suite. The smoke test builds the repository as a wheel, creates a fresh virtual environment, installs the wheel and its packaged dependencies, removes `PYTHONPATH`, and invokes the installed `sdai` console executable from outside the repository tree.

This is intentionally separate from the editable `pip install -e '.[dev]'` used to execute the test suite. Release readiness therefore depends on both source-test compatibility and a real package artifact being installable and executable.

The packaged CLI test proves:

- `sdai --version` works from the installed console entrypoint;
- `sdai init --path ...` can bootstrap an existing application root without changing pre-existing application content;
- local team-owned SDAI content remains byte-for-byte unchanged;
- a representative missing managed file is restored by `sdai migrate apply`;
- repeated `sdai upgrade` on the current scaffold is idempotent;
- the committed migration can be rolled back to the exact pre-migration state.

## Crash-safe upgrade transaction

SDAI migration apply now uses a durable prepare/commit protocol:

1. validate the complete migration plan against the current managed bytes;
2. create exact backups for stock replacements;
3. durably write an integrity-bound prepared manifest **before the first project target write**;
4. atomically write and verify every managed target;
5. durably write an integrity-bound commit receipt only after every target has reached its expected post-migration hash.

A process that disappears before step 3 cannot have changed project targets under this protocol. A process that disappears after step 3 leaves enough durable evidence to distinguish every target's recorded pre-migration and post-migration state.

On the next `sdai migrate apply` or `sdai upgrade`, SDAI detects the incomplete transaction before planning a new migration. It restores only targets whose bytes are exactly one of the two states recorded by that transaction, verifies the pre-migration state, records a recovery receipt, and then plans the requested upgrade again.

Recovery is restart-safe: if recovery itself is interrupted, a later retry accepts only the same recorded before/after states and continues toward the pre-migration state.

## Fail-closed boundaries

Automatic recovery stops without changing the ambiguous target when any target contains bytes that match neither the recorded pre-migration nor post-migration hash. It also fails closed on missing or invalid stock backups, non-canonical evidence paths, symlinked evidence/targets, conflicting transaction receipts, unsupported transaction protocol versions, or multiple concurrent incomplete migration records.

`sdai migrate plan` is read-only and refuses to produce a new plan while an incomplete transaction exists. `sdai migrate rollback` is available only for committed migrations; an interrupted transaction must first go through recovery.

Migration evidence is integrity-bound local evidence. It does not claim external identity, cryptographic approver identity, SSO/OIDC authorization, or distinct-approver enforcement. The held 0.18/#25 identity-backed approval scope remains excluded.

## Automated fault-injection evidence

`tests/test_v108_install_upgrade_rollback.py` constructs the same durable state that a process crash would leave after a prepared manifest and partial target write. The gate proves that:

- planning detects and refuses the interrupted transaction;
- retrying apply restores the partial transaction before applying a fresh committed migration;
- committed recovery-protocol migrations retain conservative rollback and idempotent repeated rollback;
- a target changed to unknown/operator-owned bytes causes recovery to fail closed without replacing those bytes;
- brownfield application files and team-owned SDAI files survive upgrade unchanged.

Existing 1.0 migration compatibility tests remain authoritative for deterministic planning, stock-vs-customized scaffold handling, manifest/target tamper refusal, symlink fail-closed behavior, machine-clean JSON, and legacy `sdai upgrade` output compatibility.
