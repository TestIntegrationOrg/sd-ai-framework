# SDAI 0.20 Release Evidence

SDAI 0.20 — Context Engine + Provider Reliability Hardening — is validated by the integrated gate in `tests/test_v020_context_provider_release_gate.py` together with the complete unfiltered historical test suite.

This document defines the stable evidence protocol. Exact pull-request head SHAs, squash-merged `main` SHAs, GitHub Actions run IDs, and final matrix conclusions are recorded on issues #259 and #27 after the corresponding immutable GitHub evidence exists. They are intentionally not written back into this file after validation because doing so would create a new, unvalidated tree and a circular release claim.

## Release boundary

0.20 completes the identity-independent context/provider hardening track built on the 0.19 Audit + Provenance foundation. It does **not** implement or depend on held 0.18 / #25 Identity-Backed Enterprise Approvals.

Local human/AI/system/workflow attribution remains provenance. Nothing in the 0.20 gate upgrades those values into externally verified identity, enterprise authorization, approver signatures, or distinct-approver enforcement.

## Integrated release journey

The release gate proves the following on a real initialized and upgraded SDAI project:

1. **Unicode/cross-platform workspace** — project paths and feature content include non-ASCII characters and remain valid on supported CI operating systems.
2. **Traceability-aware minimal context** — `AgentRuntime.build_context_plan` selects relevant feature/source context and emits only paths, hashes, sizes, exclusions, and reason codes rather than raw selected context.
3. **Provider-free context explanation** — `build_context_explanation` binds the context-plan SHA and prompt/context metrics without exposing raw secret-bearing feature content.
4. **Deterministic policy-bounded routing** — the same `RoutingRequest` produces byte-identical `sdai.model-routing/v1` output and the selected profile is an eligible policy-bounded candidate.
5. **Immutable routing evidence** — the exact serialized routing-document SHA used by provider diagnostics is the key for the persisted routing diagnostic, while the decision canonical-body SHA remains separately verified.
6. **Observable retry journey** — a deterministic observable provider emits first-output and heartbeat metadata, fails transiently once, is retried as a distinct governed attempt, and then succeeds. Retry policy/decision/summary evidence is persisted before replay.
7. **0.19 audit linkage** — each provider attempt produces started/terminal audit events and the release report verifies the append-only audit chain without acquiring or creating audit locks.
8. **Unified read-only diagnostics** — `build_diagnostics_report` and `sdai diagnostics FEATURE --json` correlate current context, historical route evidence, provider lifecycle, retry status, and audit identifiers without calling a provider or changing project bytes.
9. **Privacy** — raw selected context, explicit execution context, provider output, and provider exception text are absent from diagnostic/retry/audit operator output.
10. **Real CLI subprocess hardening** — the CLI provider runs under a Unicode workspace, preserves strict UTF-8 output, reports metadata-only first-output/heartbeat progress, and cooperatively cancels a long-running subprocess.
11. **No ambiguous replay** — an audit terminal-persistence failure after provider completion is not classified as safe to retry; the provider is called exactly once.

Focused 0.20 tests remain enabled for deeper adversarial cases such as diagnostic-persistence failure, retry-decision persistence failure, malformed UTF-8, large stdout/stderr pressure, startup failures, timeouts, routing-health tamper detection, cancellation, and canonical evidence tampering.

## Compatibility evidence

Release validation requires the **unfiltered** repository suite. Historical release/evidence gates from 0.6 through the identity-independent 0.19 foundation remain enabled; the 0.20 gate is additive rather than a replacement for those compatibility checks.

Required pull-request matrix:

- Ubuntu latest / Python 3.11
- Ubuntu latest / Python 3.12
- Windows latest / Python 3.11
- Windows latest / Python 3.12

No 0.20 PR may be merged unless all four legs are green on the exact frozen PR head and there are zero unresolved actionable review threads.

## Independent exact-main validation

After the final 0.20 gate is squash-merged, create a validation-only pull request whose head points **exactly** at the resulting `main` SHA. Do not add an evidence-only commit. Run the same full four-leg matrix on that exact tree.

The validation-only PR is closed without merge after all four jobs succeed. Issue #259 and parent #27 may close only after recording:

- frozen release-gate PR head SHA and four-leg run ID;
- final squash-merged `main` SHA;
- validation-only PR number whose head equals that exact SHA;
- independent four-leg validation run ID and conclusions;
- zero unresolved release blockers.

## Failure policy

A failed platform leg, integrity assertion, historical release gate, or unresolved P0/P1 finding blocks 0.20 completion. Fix the concrete defect on the focused release-gate branch and repeat exact-head validation; do not waive, filter, or rerun around a deterministic failure.
