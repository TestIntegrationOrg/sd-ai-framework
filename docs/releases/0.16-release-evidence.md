# SD-AI 0.16 Contract Engineering release evidence

This document is the release-readiness evidence map for deterministic Contract Engineering. The authoritative executable gate is the repository's full CI workflow: every pull request and `main` push runs the unfiltered `pytest -q` suite on Ubuntu and Windows with Python 3.11 and 3.12.

## Integrated 0.16 journey

`tests/test_v016_contract_engineering_release_gate.py::test_v016_integrated_contract_engineering_release_journey` builds a real local Git-backed SD-AI project and proves one end-to-end journey without network/provider authority:

1. initialize project policy and the engineering constitution;
2. explicitly declare OpenAPI, AsyncAPI, JSON Schema, and Protobuf sources;
3. discover and validate every declared source through the production adapter registry;
4. compare valid candidates in `full` directional mode and prove deterministic diff JSON/hashes;
5. classify a known critical breaking OpenAPI change and prove it is blocked without evidence;
6. bind architecture-approval and migration-plan evidence to baseline/candidate/diff/policy/constitution hashes;
7. prove the same critical change is allowed only after both current evidence records validate;
8. exercise the public `sdai contract inspect`, `check`, `diff`, and `gate` JSON/exit-code surfaces;
9. promote the governed candidate into current declared contract truth;
10. bind the exact allowed policy decision into contract source/symbol trace provenance;
11. link the current OpenAPI operation to requirement, task, test, ADR, independently declared approval, and migration evidence;
12. rebuild the canonical trace graph twice and prove deterministic graph/result identity; and
13. execute `sdai trace coverage --json` and prove requirement coverage plus contract source/symbol/link coverage without stale contract gaps.

This gate covers all four format adapters, directional compatibility, classification, policy precedence defaults, fresh evidence enforcement, anti-self-approval behavior, policy decision hashing, trace symbol identity, decision provenance, and existing trace coverage integration.

## Exact-head evidence protocol

Issue #209 is closed only after its exact pull-request head is green on all four supported CI legs. The exact PR head, workflow run id, and four job conclusions are recorded on issue #209 after that run completes; this avoids mutating the validated head merely to write its own SHA into the repository.

After the PR is squash-merged, the resulting exact `main` head must independently complete the same full four-leg CI matrix successfully. The merged-main SHA/run evidence is recorded on parent issue #23 before #23 is closed. This provides a non-circular, auditable release-readiness record for both the reviewed implementation head and the actual released main history.
